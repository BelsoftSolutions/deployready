No critical issues in this migration. The RLS design is sound: memberships are readable only by their owner, organizations and projects are readable only by members, and project writes require the admin role in the target org (`with check` also blocks moving a project into an org where the user is not an admin). Clients also cannot write to `memberships` or `organizations` because no write policies exist, so privilege escalation through role self-assignment is blocked.

One functional gap, not a vulnerability: there is no INSERT or UPDATE policy on `memberships`, so org admins cannot add or change members through the API. Membership management will need to go through the service role or a SECURITY DEFINER function that checks the caller is an admin.
